# 游戏开发协作指引

先判断用户要从哪里开始、交付到哪里。一个新游戏默认走「一句话 → Step 1 全套开发文档 → Step 2 按文档开发 → 试玩验收」。用户只委托设计时，交付到文档评审；明确只想聊创意或直接验证一个机制时，走与该委托相称的短流程。

## 新游戏与文档交接

1. **接到一句话。** 保留用户原话，起草一个有选择、有后果的游玩片段。把最影响玩法或工作量的一处分歧带入[设计访谈](references/dialogue-and-playtest.md)。用户可以逐轮拍板，也可以委托 Agent 选择其余细节。将授权、假设和已确认的决定分开记录。
2. **Step 1 · 交付全套开发文档。** 按[立项文档与开工评审](references/design-package.md)逐份写出本里程碑的实际内容和美术资源。复用已有成果，交付一个能打开所有材料的索引。请用户围绕一个能玩的场景评审体验、范围及关键取舍。在约定范围内完成文档包，是本阶段的独立交付物。
3. **Step 2 · 从文档开发。** 接到开发委托后，按[从文档到可玩构建](references/build-from-docs.md)核实采用的文档版本，选出首个可玩的任务，完成实现、资产接入、运行检查和记录。用户带着已有全套文档来时，直接从这里接手。已经批准或明确委托代选的内容可以沿用。
4. **试玩与后续制作。** 按[阶段与文档表](references/stages.md)选择原型、垂直切片、量产或交付阶段。保留试玩者的实际观察，项目负责人据此调整文档和后续任务。

**GitHub 仓库管理也可单独接手。** 用户选用 GitHub、项目已有对应仓库，或用户要处理游戏的 Issue、PR、试玩包或 Release 时，读[GitHub 协作与版本交付](references/github.md)，从当前委托的环节进入。若另有仓库负责人，把材料交给该负责人。离线设计和其他托管平台沿用原流程。

**外部工具参与制作。** 若某一步必须在引擎编辑器、建模、动画、绘图或音频软件内完成，读[外部工具制作与交接](references/external-tools.md)。对制作、导出、导入和运行验收分别确定执行者。项目只用本地脚本即可完成的任务沿用常规流程。

## 从现状选起点

1. 先看项目约定、用户现有决定、相关设计稿、任务单，以及最近能运行的构建或变更。区分「策划写了」「游戏里能做」「玩家试过」三种证据，记清各自对应的版本。与当前工作无关的目录可以略过。
2. 已有项目从第一个缺少依据的决定继续。手感改动从已有规则和可玩的基线开始。行为与已定规则不符时，用缺陷记录串起复现、修复和回归。单项调整只维护受影响的文档。
3. 向用户说明本轮要做出的决定，以及会交付什么。若方向已定就直接起草或执行。若缺的信息会改变玩家体验、成本或验收方法，先按[设计访谈与试玩](references/dialogue-and-playtest.md)提出最值得回答的问题。

## 每一步怎样确定文档

先找**谁要依据这份内容作什么决定**，再定载体。给当前阶段列一个小清单，每项注明「复用 / 补写 / 新建」、实际文件位置或聊天段落、要补的事实和验收者。新项目以 Step 1 的完整覆盖为准。其他专项文档按实际触发条件增补。

- 原文、构建或测试记录已经回答了问题，就引用对应章节、版本或用例。一个结论保留一处可维护的正文。
- 同一人、同一轮就能评完的小改，把目标、规则差异、验证和结论放进原任务单。跨工种需独立评审、会分别迭代，或需要交给下一位执行时，再拆出文档并互链。
- 选好载体后，在用户委托的范围内填入本轮已有的实质内容。用户只问文档规划时，交付清单、用途和就绪条件即可。项目没有既定目录又需要持久化时，可用 `docs/game/<里程碑或功能>/进度.md` 保存决策与文档索引。

## 决策、验收与续跑

- **把决定交给合适的人。** 玩家说出发生了什么，设计负责人裁定体验目标和取舍，工程或美术负责人确认各自能交付的范围。独立开发者可以兼任。能从资料查明的事实先查；可逆的实现细节按现有约定推进。用户明确委托代选时，记录委托范围、选择和可推翻它的证据。
- **只暂停依赖该决定的工作。** 每轮集中问一个会改变下一步的问题，必要时连带一两个紧密相关的问题。收到答复就把它落实成规则、样例或实验，再检查有没有会影响结果的歧义。意见冲突、方向变更、核心体验定案或承诺新的制作范围时，请有决定权的人裁定。已有明确答复直接采用。
- **按证据转换阶段。** 每阶段读阶段表最后一列。通过就进入委托范围内的下一步；证据缺失就补对应检查；失败就定位到规则、实现或体验假设并回到相应阶段。变更决定时保留旧结论和替代它的新决定，标出失效的文档、构建或用例，只重验受影响项。
- **接上团队已有的研发流程。** 团队使用工单与版本控制时，把澄清后的验收例放回原单。按项目规则确认就绪，沿用对应分支，在变更评审中链接构建、回归结果和人工体验结论。设计评审、代码评审和试玩各自保留决定人与证据。有规定的合并或发行条件，直接沿用。
- **让下一次能续上。** 用项目原有任务单或进度页记录下列最少信息。用户只要口头讨论时，用聊天摘要承接。恢复时先核对当前版本和最后一个未决项。

| 记录项 | 要留下的内容 |
| --- | --- |
| 本轮目标 | 要交什么、做到哪个阶段为止、目前在哪一步 |
| 文档与证据 | 已产出或复用的位置、构建或修订标识、覆盖了哪些验收条件 |
| 人的决定 | 谁在何时选了什么、依据或原话、将影响哪条规则；尚无结论的记为待定 |
| 下一步 | 谁要做哪个动作、看到什么结果就能继续；待确认的问题附可执行选项 |

收尾时直接给出可打开的交付物、实测结果和待定项。实际试玩、评审、发布分别按已有回执记录。制作交付包和对外发布是两个独立动作，后者依用户授权执行。
