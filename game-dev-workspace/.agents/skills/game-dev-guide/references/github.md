# GitHub 协作与版本交付

按当前委托选一段执行。先核对仓库所有者、仓库名和本次交付对象。用户把 GitHub 交给专人或另一个会话时，在本地准备交接材料，由受托方执行远端操作。已经授权的动作直接推进；只委托设计、评审或打本地包时，交付相应草稿、意见或文件。远端回读成功后，才把真实链接和状态写进项目索引。

## 立项或接手仓库

- **已有仓库。** 核对本地检出目录、远端仓库身份、默认分支、本次目标分支，以及工作区、暂存区、未跟踪文件和未合并的 PR。GitHub 上的实际默认分支和团队约定决定 PR 的目标。多人共用工作区时，保留队友的改动，只暂存本任务文件。交接记录只放不含凭据的仓库地址。
- **新建仓库。** 依据用户委托落实归属、仓库名和可见性。用户只说“用 GitHub”且未定归属或共享范围时，先产出建仓草案，创建前集中确认这两项。首次提交应能让接手者找到文档索引、启动游戏并了解所需资源。已有本地历史时先比对远端初始提交，出现分叉时保留双方历史。只在委托涵盖时修改协作者权限、分支保护或可见性。
- **游戏资产。** 源码、设计文档、工程设置、依赖锁文件和引擎要求的资产标识纳入版本管理。按实际引擎补忽略规则，例如 Unity 资源及其 `.meta` 一起提交，排除可重建的 `Library/`。大型模型、分层图、原始音频先检查仓库既有的 Git LFS 或资产库约定；用 LFS 时按选定路径配置并提交 `.gitattributes`，从干净检出验证拿到真实素材且能导入。外部资产库记录版本和取用位置。公开源码、美术源文件和成品分发分别核对素材许可。[Git LFS 文档](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage)

## 把制作任务接到 Issue、分支和 PR

| 环节 | Agent 的动作 | 留给下一位的依据 |
| --- | --- | --- |
| 任务与版本计划 | 先搜同一玩法条目、缺陷和里程碑，复用已有 Issue。新任务写玩家场景、设计章节或 ID、范围、验收例；缺陷写构建、设备、复现输入、预期与实际。一个版本内多任务可归同一 Milestone，团队已有 Projects 看板时沿用其状态 | 文档 06 的任务能找到真实 Issue；尚未建单时标“草稿”，用本地任务 ID。试玩发现能回到原任务 |
| 分支与提交 | 从团队指定基线切出或复用任务分支；未定命名时可用 `feat/<任务号>-<玩法>` 或 `fix/<任务号>-<问题>`。检查提交范围，把相互依赖的代码、设计修订及资产标识一起交付。推送前核对远端、分支与待推提交 | 工作分支、基线和待审提交 SHA；并行工作落在各自分支或 worktree。推送被拒时先读取分叉原因，保留其他人的提交 |
| PR 与评审 | 查同一来源分支和目标分支的已有 PR，更新对应 PR。正文写设计依据、玩家可见变化、怎么运行、实测和待测；画面或手感改动附对应构建的截图、短片或试玩入口。核对本轮提交的 CI 和评审结论 | PR 链接、base/head、已测 SHA、构建入口、未决项及合并状态。新提交影响原证据时重跑受影响项 |

同一 Issue 若还等真人试玩，PR 正文普通引用 `#编号` 并列出待测项。任务满足关闭条件、且 PR 目标是默认分支时，可用 `Closes #编号`。PR 合入集成分支后，按项目约定跟进最终合入和实际 Issue 状态。合并前核对仓库要求的检查、审批及其对应版本，合并后回读目标分支的合并结果。[Issue 与 PR 关联规则](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

## 试玩构建与 Release

1. **交试玩包。** 记录平台、运行入口、实际构建输入的 SHA，以及产物名。使用现有 CI 时，从对应工作流运行中核对实际检出的提交，包括 PR 测试合并提交的情况。将构建、测试报告和必要的资源一同交给试玩者，注明访问条件与过期时间。只做本地构建时交本地包及校验值；若构建包含未提交改动，先说明差异，待确定可复现基线后再关联发行标签。[Actions 构建产物](https://docs.github.com/en/actions/tutorials/store-and-share-data)
2. **准备版本。** 采用项目版本号，核对 tag 指向的提交与经过验收的构建来源。合并、压缩提交或重建导致 SHA 变化时，重新核对差异及受影响检查。已有同名 tag 指向别处时，保留原 tag 并处理版本冲突。Release 草稿列玩家可见变化、目标平台、操作说明、已知问题，以及每个可玩附件的文件名和校验值。
3. **按委托交付。** 区分本地候选包、Release 草稿、预发布和正式发布。获得对应发布授权后上传验收过的可玩包，回读 Release 的 tag、状态及附件；从接收者可访问的入口下载、比对校验值并检查解压启动。记录验证设备，缺少的平台标待验。GitHub 自动生成的 Source code 归档供取源码，给玩家的链接应指向实际可玩的附件。发布出错时保留原版本记录，按项目规则准备修正版。[GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)

## 给仓库负责人的交接

交付物随委托裁剪。例如策划只交下一轮的**输入**：仓库及里程碑、已定设计版本、原任务 ID、Issue 草稿、预期的试玩证据。仓库负责人完成操作后回填**结果**：Issue / PR 链接、目标分支和提交、构建或 Release 链接、实际检查结论、仍由谁处理什么。发生权限或网络错误时，先回读目标对象，确认上一次写入是否生效，再决定补做哪一步。
