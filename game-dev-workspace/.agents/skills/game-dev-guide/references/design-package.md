# Step 1　从一句话到可开工的文档包

这一步要让另一位开发者只凭交付材料，就能判断首个可玩版本要做什么、从哪做起，以及怎样算做到了。优先用项目已有目录和格式。没有约定时，把索引、下面六份正文和随附资源放到 `docs/game/<里程碑>/`，在索引使用相对链接。文档覆盖本轮同意制作的内容，后续扩展只登记边界。

## 从玩家的一分钟开始访谈

先把一句话还原成玩家看到什么、做什么选择、世界如何回应。第一轮让用户选择最值得保留的体验；有分歧时给两个手感、难度或内容成本明显不同的游玩片段。接着用已有信息收敛平台与输入、目标玩家、团队与期限、这轮愿意舍弃什么。每轮先把答案写进相应草稿，再追问会改变设计的下一项。

临时缺资料时可以用标明的假设写草案，给用户看具体场面、画面或台词。用户说“细节你定”时，记录委托范围，在其中选一个可实现的版本。方向已明确就直接完成文档。有关乐趣、可读性和性能的预测在试玩或测量前保留为待验证。

## 实际交付什么

| 文件 | 最少要写到什么程度 | 谁能拿它完成什么动作 |
| --- | --- | --- |
| 00 文档索引与决策记录 | 保留原始一句话，写里程碑、交付范围、每份正文和资源的链接、采用的版本、关键决定与待决项。评审后记下决定人及采用范围 | 接手者一次找到当前依据，知道哪里能开工、哪里要等决定 |
| 01 项目计划书 | 写目标玩家与体验、一分钟游玩片段、交付平台、首版范围与舍弃项、可玩里程碑、先后依赖和最大风险。人员与日期沿用实际约束，估算写明假设 | 制作人能回答“时间缩短时先保什么”，并指出这次要交的构建 |
| 02 玩法策划 | 写核心循环、操作、状态变化、反馈、成功与失败、重试，展开首个关卡或一局的完整流程。关键数值写单位与初值；每条核心规则给正常例和边界例 | 策划和程序能独立演算一局，对同一输入得到一致结果 |
| 03 技术栈与工程方案 | 依据平台、团队和现有工程选择引擎或运行时、语言、输入与构建方式，说明理由。列场景和模块职责、数据结构、资源接入路径、启动办法与最大技术未知项。新项目尚未试过的命令标记待验证 | 工程能搭出首个场景，知道规则事件由谁发出、资源由谁加载以及如何在目标平台检查 |
| 04 美术设定集与设计资源 | 定义镜头、比例、构图、色板、轮廓、UI 层级、关键动作与反馈。为首个可玩场景交付能打开的视觉样例，如带图例的界面线框、角色比例稿或关键帧。资产清单逐项给出用途、尺寸或单位、格式、导出与接入位置、状态及可用来源 | 美术可以照样例制作同类资产，程序可以把占位或成品接入正确状态。提示词附在制作说明里，实际素材另列文件与状态 |
| 05 文稿、游戏内日志与演出台本 | 写实际可用的开场、引导、交互、失败与收束文案。按关卡写日志条目、角色台词及演出台本，覆盖本轮玩家会走到的分支。每条注明内容 ID、触发条件、说话人或载体、确切文字、呈现时机、重复或跳过规则及音画提示 | 编剧能通读场景，程序能挂触发器，音画能找到 cue。纯机械或无对白作品以真实提示、图标演出或无字分镜覆盖相同事件；在索引说明日志、对白的适用范围 |
| 06 开发任务与验收计划 | 把首个可玩回路拆成有依赖的任务。逐项注明引用的玩法、资产、文稿、技术位置，完成条件与复测场景。列目标设备、关键功能用例、真人试玩要回答的问题和交付条件 | 开发者能选出首个可执行任务，测试者有输入、可观察结果和证据位置 |

资源状态要能区分「已交付、可打开」「占位可用」「计划制作」。有绘图能力时，用它制作当前评审要看的样例。缺少专用工具时，可交付自制 SVG、带标注的线框图或分镜；明确委托的最终原画、模型、音频仍按实际完成度记录。引用现成资源时标注来源和使用条件。

需要用外部软件制作或接入成品时，按[外部工具制作与交接](external-tools.md)填写 03 的工具、版本与运行方式，04 的可编辑源件、交换格式和目标规格，06 的执行者、回传件与游戏内验收场景。沿用同一个资产或任务 ID。

只有会改变制作或验收的专项资料才展开。例如联机项目增加同步与断线恢复，叙事项目增加分支图，节奏游戏增加音乐时序表，路演或比赛交付增加逐段演示台稿（画面、操作、解说词、时长、切换 cue）。开发过程的变更日志放在索引；玩家能读到的世界内日志属于文稿。

项目采用 GitHub 时，按[GitHub 协作与版本交付](github.md)补充现有文档。00 记目标仓库、设计基线和仓库负责人，03 记工程与大资产的存储约定，06 把可独立验收的任务对应到已有 Issue 或待建草稿。这些内容由原来的文档承载。只委托设计时，把下一位负责人需要的建仓或建单材料随文档交付。

## 用同一条事件审一遍文档

例如玩家第一次接通废站电台。玩法条目「调谐」写何时算锁定频率；技术方案在进入锁定状态时发出一次事件；美术资源表给出锁定灯的形状和状态图；台本写明记录员此时说「听见了，别松手」，字幕持续多久；游戏内日志列出确切文字及再次进入时的行为。任务引用这些条目，验收者可以实际触发两次，检查规则、信号、字幕和日志条数。这个例子只示范连接方式，项目应使用自己的事件与内容。

提交评审前，逐条走通首个回路，核对玩法、工程、资源、文稿和验收是否引用同一版本，所有链接能打开；检查失败、重试或退出时也有明确结果。把冲突写在具体条目下，标出影响的任务，请负责人裁定或按已有委托处理。有未决项时写清哪些任务仍可开工。

向用户展示一分钟游玩片段、可直接打开的整包索引、实际视觉样例和会影响开工的取舍。交付文档委托即可在这里结束。用户要求继续开发时记录采用的基线（提交号、修订号或日期版），按[从文档到可玩构建](build-from-docs.md)接手。
