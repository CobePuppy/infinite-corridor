# 外部工具制作与交接

把一项真实操作当作起点，例如“把带开门动画的模型接进试玩关卡”。同一台机器可能能运行建模工具，却打不开目标引擎。逐步判断谁能执行，每一步留下下一位可以直接使用的产物。

## Step 1 · 确定制作链

先查项目已采用的编辑器版本、插件、导入预设、已有同类资源，以及团队平时怎样生成构建。有现成流程就选一个代表资源走通。新项目只问会改变交付的取舍，例如美术是否要继续编辑源模型、哪位同事能在目标平台验收。版本和能力尚未实测时记为待核实。

在原资产清单或任务单填写下面四项。纯工程任务可把“资产”换成关卡场景、音频库或平台构建。

| 交接内容 | 写给下一位执行者的信息 |
| --- | --- |
| 输入和目标 | 设计条目、资产 ID、实际源文件或参考、预期玩家行为、使用它的场景或平台 |
| 工具与分工 | 工具和项目版本、已有脚本或预设位置、谁做源件、谁导出、谁能在目标工程验证；未确定的负责人写待定 |
| 输出约定 | 可编辑源件、交换文件、随附贴图等依赖、目标工程位置。按本项填写影响结果的规格，例如模型的单位、朝向与枢轴，动画片段和循环方式，音频的声道与循环点 |
| 验收与回传 | 一个可复现的场景、操作和预期，必要的边界例；回传文件或工程修订、工具版本、导入日志及场景或构建证据 |

## Step 2 · 选择能实际执行的方式

1. **有可用的自动化入口。** 优先用项目已有 CLI、批处理、导出脚本或已连接的编辑器接口。在委托范围内先核对项目与版本，在独立输出位置跑一个样件，检查能否重新打开、导入及播放，再扩大到其余资产。记录实际使用的参数或预设及输出。更换引擎版本、安装付费插件、上传源资产等改变项目环境或共享范围的动作，按相应授权处理。
2. **需要编辑器界面。** 若当前会话可操作目标编辑器，按项目流程完成具体步骤，保存工程并在目标场景检查。需要美术判断时把同一镜头下的候选效果交负责人裁定。仅能打开软件、读取文件或生成脚本时，把已实测的能力写清楚。
3. **某一步只能由人执行。** 给能使用软件的人一张操作单：打开哪个文件和场景、使用哪个导出或导入预设、改哪些值、保存到哪里、怎样检查结果、回传哪些文件或证据。未运行的辅助脚本注明待运行。其间可用已约定的占位资源继续独立工作；外部结果返回后，从该交接点继续接入和复测。

进度记录用实际结果，例如“源件已保存 → 文件已导出 → 引擎已导入 → 场景已验证”。需要交付目标平台构建时，再记录该构建的运行结果。每次只更新取得证据的步骤。发现问题保留原件，定位到产生偏差的环节：例如导入后门绕中心转，先比对源件枢轴与引擎层级，再决定该重导模型还是修正场景绑定。

**示例：Blender → Unity 的机关门。** 假设本项目约定保留 `.blend` 源件并以 FBX 交换。美术交回带门轴的模型、开门片段、贴图和导出预设。能操作 Unity 的人按项目版本导入，在约定测试场景触发开门，核对门是否绕铰链转、动画是否按策划停住，以及通行时碰撞是否解除。若 Agent 只拿到 FBX，可以检查文件和依赖，列出上述验收步骤，把引擎导入和游戏内表现交给持有目标工程的人验证。
