# Step 2　从已确认的文档到可玩构建

## 接手基线

读取文档索引和本轮采用的版本，核对项目当前仓库、已有构建、用户委托的开发范围。已有自己的策划、资源表或任务系统时，复用实际名称和链接。若任务只是做计划，交付到任务拆分即可。受托开发时沿以下步骤走到运行验证。

使用 GitHub 时，先按[GitHub 协作与版本交付](github.md)找回任务对应的 Issue、工作分支及已有 PR。把实测构建对应的提交、证据和剩余试玩项带回同一个 PR；达到版本交付阶段再处理 tag 和 Release。

遇到依赖编辑器的工序，按[外部工具制作与交接](external-tools.md)核实当前机器能执行哪几步。把已导出的文件、目标引擎是否已成功导入、是否在场景或构建中验证分别写回同一任务。换机器或换人后从第一个缺少证据的步骤继续。

1. **选一段能玩的闭环。** 从首个里程碑选出玩家能进入、操作、得到反馈、成功或失败并重试的一段。已有项目优先沿真实入口修改。列出这段会消费的规则、资源与文稿；读取对应的工程约束。发现规则、触发器或关键素材互相矛盾，标出冲突和受影响任务，请有决定权的人选择；并行推进已明确的工作。
2. **把依据落到任务。** 每项用一行串起「文档位置或 ID → 要改的场景、模块或配置 → 要接入的资产与文稿 → 可观察的验收行为」。用现有任务编号就够。把首个可玩场景放在依赖顺序中，避免先造后续关卡才会用到的系统。标明允许使用的占位资源及替换条件。
3. **从实际入口做完并运行。** 按依赖实现最小闭环，使用台本给出的原文与触发条件，按美术资源规格接入。运行工程已有检查，再从玩家入口走一遍正常路径和一条边界路径。保存构建或修订标识、运行方法、观察结果和对应证据。执行条件欠缺时，保留已验证部分和具体未测项。
4. **用偏差决定改哪里。** 实现偏离已定规则，修实现并复测。原有设计需要改变体验或范围时，先写变更提案和受影响的条目，由负责人裁定或在既有委托内作出决定，再同步权威文档、任务和验收例。规则正确但手感存疑时，用[试玩记录](dialogue-and-playtest.md)验证，保留测试者身份类别和构建版本。
5. **交回可玩的结果。** 给用户构建入口与操作说明、完成的任务及其文档依据、实测结果、剩余占位或待试玩项。下一位接手者能凭索引找到采用的设计，凭验收记录复现同一结果。

例如任务来自“首次接通电台”。程序接入锁定事件、锁定灯状态图、字幕和日志正文后，测试者按策划给出的条件首次接通，核对台本原句和新增日志；随后退出再进，检查是否按重播规则处理。证据落到该任务的回归记录，后续改台词时可查出需复测的场景。
