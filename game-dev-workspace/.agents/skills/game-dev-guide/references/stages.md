# 阶段与文档表

各行描述一个决定及其证据。新项目先用[立项文档与开工评审](design-package.md)准备开发基线。表中的立项、玩法澄清是 Step 1 的工作；原型、切片和集成是 Step 2 常用的制作里程碑。已有项目可直接选当前行。

| 阶段与要做的决定 | 进入时先看 | 本阶段需要的内容 | 人参与什么 | 走出这一步的依据 |
| --- | --- | --- | --- | --- |
| 立项与范围：这轮要让谁玩到什么 | 一句话点子、已有承诺、平台、人手和期限 | 一页概念稿写清玩家、一个反复做的选择、期待的感受、最小可玩范围及本轮舍弃项 | 创作者讲一个典型游玩片段，制作负责人确定时间冲突时优先保什么 | 有可复述的体验目标、可承受的范围，以及准备验证的首要未知项 |
| 玩法澄清：玩家能如何行动 | 概念稿或现有玩法、玩家反馈、已有配置 | 核心循环和玩法规格写明触发、输入、状态变化、反馈、成败与重试；补一个正常例和一个会引发争议的边界例 | 策划用实际场景裁定边界，例如同时抵达终点且生命归零如何结算 | 关键例子的预期可执行，已定规则与待试参数均可识别 |
| 原型：这条机制值得继续吗 | 待验证的假设、当前基线、目标设备或输入方式 | 原型卡写明最小场景、只改哪个变量、观察什么、何时停止；附可玩入口、版本和对应试玩记录 | 试玩者实际操作，设计负责人依据观察选择保留、调整、再试或舍弃 | 可玩构建能覆盖问题，记录给出证据支持的决定。体验仍待定时保留该状态 |
| 垂直切片与制作计划：能否按这个质量和成本完成 | 原型结论、资源与技术限制、目标品质样例 | 定义一段可从头玩到尾的代表内容、临时与最终资产、目标设备表现、可删范围；计划列任务、负责人、依赖、验收点。先准备切片，再以实测校准量产估算 | 策划、美术、工程对同一段可玩内容评审，制作负责人处理质量、内容量与日期之间的取舍 | 切片在约定设备跑通，关键品质与成本有依据，制作范围获确认。只委托计划时交付计划及待验证项 |
| 制作与集成：功能能否进入可玩版本 | 已定范围、规则、任务与资产状态 | 功能任务写输入、预期和验收例；记录场景或资源标识、集成版本、实现差异及受影响测试。跨工种交接按下表补资料 | 执行者验证接入，影响手感、轮廓识别或范围的偏差交相应负责人裁定 | 在实际游戏入口能触发、体验、退出或重试，标明构建与剩余缺陷 |
| 试玩与验收：该修哪里、能否交付 | 验收例、目标玩家与设备、候选构建、已知问题 | 测试记录写环境、步骤、预期、实际和证据；试玩记录写玩家做了什么、原话和判断；缺陷单关联复测版本 | 工程核对实现，真人试玩回答体验问题，负责人按观察判定接受、返工或带已知问题交付 | 约定的技术和体验项目各有结果；未测项、接受的风险及决定人可查。阻断项回到对应阶段复验 |
| 交付与复盘：别人拿到后能否使用 | 验收结论、交付对象、平台与用户约定 | 交付说明列准确版本、构建入口、启动与操作、已知问题；有发行委托时补发行清单、恢复方式和责任人。下一轮确有安排时记录优先验证项 | 接收者按说明使用构建；需要发行决定时由对应负责人给结论 | 完成本次约定的交接并保留证据。候选包、已交付、已发行各记真实状态 |

## 有哪些情况值得另写专项内容

| 实际触发条件 | 补到哪里、至少写什么 | 谁如何使用 |
| --- | --- | --- |
| 作者、设计师和程序对关卡节奏理解不一 | 在关卡草图标出首次教学、变式、失败重试点和预期路线 | 关卡作者据此搭灰盒，试玩者的走法用来检验引导 |
| 动作时机、轮廓或声音承担玩法信息 | 在美术、动画或音频规范中标出玩家要读到的信号、出现时机、可区分的样例和游戏内验收场景 | 美术和音频据样例制作，策划在目标分辨率和混音下验收 |
| UI、控制方案或无障碍设置影响可操作性 | 在交互流程标出输入设备、焦点移动、确认与取消、反馈替代方式 | UI 和测试从实际入口走完成功与返回路径 |
| 成长、经济或数值曲线需要多人调参 | 在平衡表记单位、基准版本、典型局输入和目标结果；数据配置已有就链接 | 策划改一组值，测试用同一场景比较前后表现 |
| 叙事会改变玩家选择或内容制作 | 在分支表记触发条件、玩家可见信息、后继状态和可达结局 | 编剧、关卡与测试按同一组选择走通分支 |
| 联机、存档、物理或性能预算影响可行性 | 在技术方案记录目标设备、需持久化或同步的状态、失败恢复、待测预算和复现方法 | 工程验证最小路径；实测超预算时由负责人决定降级或改范围 |
| 多人制作同类资产或需要外部交接 | 在资产清单记源文件、导出规格、使用范围、接入场景、负责人及状态 | 制作人可区分占位与最终素材，接收者能重新导入并检查 |

## 两条短路径

- **已有规则的局部缺陷。** 例如菜单关闭后角色仍被锁定。在原任务写进入条件、复现输入、预期和实际，补修复构建与复测结果，再检查相邻的暂停或手柄返回路径。若策划已确认关闭菜单应交还控制，就能直接验证。
- **用户明确只验证一个机制。** 一页原型卡兼作概念稿、规则和试玩记录。写一个动作、一段可重试的场景、一个要观察的玩家行为和截止点。若用户要求完整文档，时间限制用于缩小玩法或内容量，仍按 Step 1 交齐材料。
